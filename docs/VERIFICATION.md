# Verification evidence

Verified locally on 2026-09-27 with the pinned dependencies. This is a small local demonstration, not a production certification.

1. `npm run check` passed. `npm test` passed 18 isolated tests. They cover exact prices, the $0.50 approval boundary, the $0.90 purchase cap, approval binding and review tampering, duplicate and concurrent calls, uncertain reservations, definitive failure release, process restart persistence, saved-key recovery, exact authorization slots, provider policy shape, UTC completion boundaries, and report deduplication. These use fake transport and do not establish provider enforcement.

2. `npm run eval -- --verbose` ran Eve's actual eval runner against the configured model with a fresh isolated fake ledger. All five evals and 33 assertions passed. The conversations exercised premium coffee, 40 drinks with an attempted chat override, native approval cancellation, native approval acceptance and replay, and exhausted budget with claimed authority. Approval input contained the saved exact review string. Fake submission counts were checked; rejected and refused cases submitted nothing.

3. A real $0.25 coffee send completed through the Catena SDK. Separately, a real natural language snack request prepared $0.60, paused in Eve, and resumed after the human operator selected approval. Catena reported processing and later completed. The ledger retained the native human responder and matching saved purchase approval digest. Two subsequent calls for that paid purchase returned the same intent. The live ledger contains exactly two submitted purchases totaling $0.85. The confirmed demonstration allowance is exhausted; payments are disabled by default.

4. The initial live approval used the saved purchase ID and purchase summary. Inspection afterward found that Eve's native prompt uses tool inputs rather than the dynamic tool label. The final implementation therefore includes and validates an explicit review string containing the amount, items, vendor, and recipient in the approval input. That strengthened prompt was verified through native fake evals and tampering tests. It was not retested with another real transfer; no further spending was authorized.

5. Read-only Catena inspection confirmed a dedicated base policy with USD monthly and purchase block rules of $500 and $0.90, the restricted existing recipient, and sufficient same-network funds for the observed payments. This proves configuration and successful allowed payments. Provider refusal at either spending boundary was not induced or observed. The local 40-drink refusal is not evidence of a Catena rejection.

6. Manual report execution and refresh produced a single live report for September with $0.85 settled and $0 unresolved. The conservative lifetime comparison was $499.15; this is not available money or remaining test authorization. Provider availability remained unknown. Private identifiers, original records, and payment references are retained only in ignored local storage.

7. The built Eve application ran locally with `TZ=UTC` and isolated fake storage. A temporary `* * * * *` schedule fired automatically at 19:09:00.035 UTC and 19:10:00.012 UTC. Both durable run records had source `schedule`, while the inbox retained one previous-month report. This was clock-driven execution, not a manual dispatch. The process was stopped, the intended `0 9 1 * *` cadence restored, and the final build completed successfully. Eve discovery reported four tools, one monthly schedule, and zero errors or warnings. The schedule must be started and kept running by the operator; it is not installed as a background service.

The build succeeded with upstream optional sandbox tracing and bundler debug-name warnings. No sandbox tool is enabled. Catena's monthly window, timezone, reset boundary, timestamp attribution, pending accounting, and current usage API remain unverified. The stricter local lifetime guard is deliberately retained. The UTC report is complete as a local report, but provider-window accounting parity is not complete.
